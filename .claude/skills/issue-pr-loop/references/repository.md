## Owner-reserved decisions

No issue class is reserved for the owner beyond the `[human]` category in `SKILL.md` § Resolve, do not defer. A breaking change is allowed on a milestone that permits breaking changes.

## Issue labels

Priority labels are `P0` to `P3`: read them as `priority:critical`, `priority:high`, `priority:medium`, and `priority:low` in `pick-an-issue.md`. The repository has no `ci` label; judge pipeline-health issues by content.

## Repository rules

- Run local .NET commands through `scripts/Invoke-AgentDotNet.ps1` using in-process PowerShell array binding. Respect its time/memory limits; never build/format the all-project solution or execute the build pipeline without explicit authorization.
- Change generators/scrapers and regenerate options; do not hand-edit generated output or preserve obsolete generated APIs with shims.
- For a generator or scraper fix, open the PR with the generator change and its tests as soon as they pass locally. Do not hold the PR until hosted regeneration finishes: dispatch the [Generate CLI Options workflow](../../../../.github/workflows/generate-cli-options.yml) when the change needs fresh output, name the run in the PR body, and report `opened #N closing #M`. When an issue can only move after a dispatched run, report `waiting #N: run <id>` instead of adding `on-hold`.
- Generated output ships through the automated `[Automated] Update <tool> CLI Options` PRs, not through issue PRs or issue chains. A generator or scraper issue is delivered when its generator PR merges: after the merge, dispatch generation for the affected tools with `create-pr=true`, link the run on the issue, and close the issue when its remaining acceptance criteria concern only the regenerated output. Do not file "regenerate and validate" sub-issues, and do not carry generated files in an issue PR to beat the freshness check: every generator merge makes such snapshots stale. Close existing issues of that kind as superseded by the automated PR or the dispatched run.
- Follow [pull request maintenance](../../../../AGENTS.md#pull-request-maintenance) for autogenerated CLI options PRs, closed-PR CI cancellation, and review-thread resolution. Apply it before choosing repair work; some PR categories require closure and a linked issue instead.
- Stop only services created for the current worktree; shared lock Redis must remain running.

## Shipping

- Follow local validation, resource limits, target frameworks, generated-code boundaries, and performance requirements. Use TDD for bugs and behavior changes where feasible; explain exceptions. Run focused and relevant broader checks, including docs and frontend checks when affected.
- Review the full diff for correctness, reuse, and efficiency (`/simplify` when available, otherwise equivalent review). Preserve performance and contracts, and batch related fixes into one push.
- Use commentary while active.

## Worktrees

Add to the shared-checkout capture in `SKILL.md` § Isolation and ownership:

```powershell
$repoName = ($repoSlug -split '/')[-1]
$worktreeRoot = Join-Path (Split-Path $repo -Parent) ($repoName + '-worktrees')
$evidenceRoot = Join-Path (Split-Path $repo -Parent) ($repoName + '-evidence')
```

- Verify the repository and intended base; examples use `origin/main`. Use a writable temporary `<repoName>-worktrees` root if needed.
- No sparse-checkout or custom push refspec applies here.
- Create a PR's detached worktree with `git worktree add --detach --lock --reason 'PR checkout setup'`, then run `gh pr checkout <N>` in it. Wrap checkout and lock-path registration in `try/finally`: in `finally`, run `git worktree unlock <absolute-path>` for the temporary Git lock created by this setup, including when checkout or registration fails, before the outer Redis release. Report an unlock failure and preserve the path for recovery. The temporary Git lock protects setup from concurrent cleanup; Redis remains the ownership authority.
- Keep explicit lock names when registering a path.
- Use repository scripts for merged-worktree cleanup; `[gone]` or ancestry alone is insufficient. Preserve dirty, locked, open-PR, harness-managed, and locally divergent worktrees; the sweep removes a merged or closed item's checkout only after retaining its branch and uncommitted work under `retained-worktrees/` ([lifecycle](../../../../scripts/WorktreeLifecycle.md)).
- Inspect untracked source before cleanup: scripts may clear build artifacts. Manually remove abandoned worktrees only after verifying repository/path, ownership, and absence of valuable unpublished work.
- Stop only services, processes, and containers started for this worktree. Never blanket-delete containers or volumes, or stop shared lock Redis. Follow local lifecycle guidance; use Aspire only where an AppHost exists.

## Output locations

Write nothing loose beside the repository. Every file an agent produces outside its worktree has one home, so cleanup can find it:

- Evidence (build and test logs, reports, PR and comment body drafts, diffs, validation projects) goes in `<repo-parent>/<repoName>-evidence/<lock-name>/`, for example `$evidenceRoot/issue-1234/build.log`. `scripts/Remove-MergedWorktrees.ps1` deletes a `pr-<N>` or `issue-<N>` entry once that item is closed (merged or not) and no registered worktree uses it, and any other entry once its newest file is older than 7 days (`-EvidenceRetentionDays`). Release keeps the evidence of an open item.
- Long command output (builds, tests, `gh api` dumps, logs) goes to a file under the evidence root.
- Throwaway checkouts and baselines are worktrees under `$worktreeRoot`, never plain copies.
- Downloaded SDKs and CLI tools go in `<repo-parent>/toolchains/<name>-<version>/`, shared by every repository.
- Never write to `<repo-parent>` itself or to the shared checkout.

## Retained work

The sweep removes the checkout of a merged PR or closed item itself but keeps its work: the branch stays, uncommitted changes go to `retained-worktrees/<item>-wip-<sha>` (inspect with `git stash show -p --include-untracked <branch>`, restore with `git stash apply <branch>`), and a detached HEAD to `retained-worktrees/<SHA>`. Recover from those branches the same way as [recovery.md](recovery.md).

## Review cycle

Run under the PR lock.

- Inspect all review surfaces, including pagination and replies: REST `pulls/<N>/reviews`, `pulls/<N>/comments`, `issues/<N>/comments` under `repos/{owner}/{repo}`, and GraphQL `reviewThreads` with IDs, resolution state, bodies, authors, and timestamps.
- Never infer a reviewer's surface from its identity. Treat a conversation comment that carries findings or a verdict as a review; it has no thread to resolve, so disposition it with one PR comment that quotes or links it.
- A `COMMENTED` review body can block with zero unresolved threads. Address outstanding concerns, `CHANGES_REQUESTED`, current inline findings, and unresolved threads. Empty acknowledgments are non-blocking. Assess older findings against the current head and later discussion; uncertain concerns block merging.
- Verify every finding against code and classify it. **Blocking**: a correctness, concurrency, security, contract, or performance defect, or missing tests for changed behavior. Fix each valid blocking finding in this PR. **Non-blocking**: naming, style, wording, optional refactors, extra tests for unchanged behavior, and "consider" suggestions. Implement a non-blocking suggestion only when it is small and you already push a blocking fix. Otherwise decline it in the disposition with a one-line reason and push nothing for it.
- Decline a wrong finding with evidence from the code. Move architectural work that is genuinely out of scope to a filed follow-up issue, linked in the reply. "Not done" or "left as is" without a classification, reason, or linked issue is not a disposition.
- Reply once per review covering each finding, and reply on each thread. Discuss disagreement once; implement reaffirmed blocking feedback. A disposition-only reply on the current head needs no new push, so it does not start another review cycle.
- Resolve every review thread, whether a human or a bot opened it, as soon as it is dispositioned: the fix commit is in the remote PR head and the reply names it, or the reply pushes back on the finding with evidence. Do not wait for another review/CI cycle to resolve a dispositioned thread; that cycle still gates merging. Leave a thread open only while it has no disposition: the fix is not pushed, the item waits on the user, or the reviewer replied after your disposition.
- On each later review cycle, re-fetch every thread, resolved ones included; a reviewer reply newer than your disposition reopens it: run GraphQL `unresolveReviewThread` and handle it as reaffirmed feedback.
- Reply to addressed review-body findings and request re-review when an outstanding changes-requested review needs updating; do not dismiss reviews to bypass approval requirements.
- Use GraphQL `resolveReviewThread`, then re-fetch reviews, threads, checks, and head SHA.

## Draft review lifecycle

[draft-review.md](draft-review.md) is the PR review lifecycle.

- Draft policy: [AGENTS.md](../../../../AGENTS.md#pull-request-maintenance) applies this lifecycle to every agent-created PR, including work outside the loop. Before creating or promoting a PR from an existing worktree, re-read `AGENTS.md` and this skill from the shared checkout; branch copies can predate the current policy.
- Claude: [Claude Code Review](../../../../.github/workflows/claude-code-review.yml) reviews drafts on open, reopen, and every push, and does not run again on `ready_for_review`, so the draft review of this head satisfies the arming gate. A trusted step publishes each round as a `COMMENTED` review by `github-actions[bot]` headed `## Claude Review`. Its positive verdict for the current head is the footer `<!-- REVIEW_VERDICT: CLEAR HEAD: <full-head-SHA> -->`; `BLOCKING` lists findings. When no review exists for the current head because the run failed, dispatch the trusted workflow with `gh workflow run claude-code-review.yml --ref main -f pr_number=<N>` and read its review before marking ready.
- Codex: `chatgpt-codex-connector[bot]` posts a `<!-- codex-pull-request-review-summary -->` issue comment. Its `codex-review-state:v1` payload is a positive verdict only when `code_review` has the exact full current-head `commit_sha`, `status: completed`, `has_any_findings: false`, and `has_unresolved_findings: false`. Ask it to name the reviewed head: append `Please review current head <full-head-SHA> and identify the reviewed commit in your verdict, or add a thumbs-up to this request if clean.` to each draft request.
- Other connected reviewers (Greptile, CodeRabbit) may also comment. Their findings are feedback to disposition, not required approvals; CodeRabbit often reports only a rate limit.
- Draft CI: the [.NET](../../../../.github/workflows/dotnet.yml), [distributed template smoke](../../../../.github/workflows/distributed-template-smoke.yml), [Go validation](../../../../.github/workflows/go-validation.yml), and [docs deploy test](../../../../.github/workflows/deploy-pages-test.yml) workflows skip every job before allocating a runner on draft PR events. `ready_for_review` starts the `.NET` caller and its selected reusable workflows; `converted_to_draft` cancels an in-flight run through workflow concurrency. Main pushes use the same path routes; a manual `.NET` run validates every route. While draft, the required `pipeline (ubuntu-latest)` check is absent, so branch protection waits for the ready run: a job skipped by `if:` reports success under its literal name, so the required aggregator takes its name from a one-entry matrix, which stays unexpanded when skipped. `scripts/Assert-PrGreen.ps1` denies drafts and ignores checks of a cancelled run that a later run of the same workflow superseded on the same head.
- Auto-merge: branch protection requires only `pipeline (ubuntu-latest)`, the strict aggregator of every applicable `.NET` workflow job. Path routing in `scripts/Resolve-FullPipelineValidation.ps1` invokes the reusable distributed template smoke, Go validation, and docs deploy test workflows; the required aggregator checks their results, so native auto-merge waits for them. Unrelated routes skip without leaving absent required checks. [Disarm auto-merge](../../../../.github/workflows/disarm-auto-merge.yml) turns auto-merge off on every push to an armed PR.
- After promotion, read any automatic reviews that readiness triggers; on a blocking finding, run `gh pr merge <N> --disable-auto` before fixing it. Any push disarms auto-merge, so re-arm only after the new head's reviews and dispositions.
- Automated review rounds (rework budget): count Claude Code Review rounds as current-format reviews, not issue comments: `gh api --paginate "repos/{owner}/{repo}/pulls/<N>/reviews" --jq '.[] | select(.user.login == "github-actions[bot]" and (.body | contains("<!-- REVIEW_VERDICT:"))) | .id' | wc -l`.

## Merge protocol

- After the lifecycle, arm native auto-merge with `pwsh scripts/Enable-AutoMerge.ps1 -Pr <N>`. It runs `Assert-PrGreen.ps1 -ForAutoMerge`, which accepts pending or not-yet-started CI but denies drafts, conflicts, failed checks, a current head without a CLEAR Claude verdict, actionable reviews, and unresolved threads, then arms a squash merge pinned to the validated head. GitHub waits only for branch protection's required checks ([Draft review lifecycle](#draft-review-lifecycle)).
- The conditions below apply to an immediate merge, for a PR whose CI already passed while not armed: confirm every one, then invoke `Merge-Pr.ps1`.
- Merge requires an open, ready-for-review (not draft) PR; `MERGEABLE` and `CLEAN`; every applicable check present, terminal, and passing (`SUCCESS`, `SKIPPED`, or `NEUTRAL`, with successful legacy commit statuses); no unresolved threads, unaddressed comments, or outstanding review-body concerns; approval when required; and a bot review/CI cycle after the last fix push. Missing expected checks and nonterminal checks block merging. Reassess if the head changes.
- `Merge-Pr.ps1` calls `Assert-PrGreen.ps1`, merges on a passing mechanical gate, and cleans up. Judge review dispositions and approval yourself.
- Never merge or arm with `gh pr merge` or `gh pr merge --auto` directly; use these wrappers. Disarming with `gh pr merge <N> --disable-auto` is allowed.

## Issue relationships

Native relationships take the REST numeric issue `.id`, not the issue number or `gh issue view --json id` (a GraphQL ID). Pass it with `-F` so it is sent as an integer:

```powershell
$childId = gh api "repos/$repoSlug/issues/<child>" --jq .id
gh api "repos/$repoSlug/issues/<parent>/sub_issues" -X POST -F "sub_issue_id=$childId"

$blockerId = gh api "repos/$repoSlug/issues/<blocker>" --jq .id
gh api "repos/$repoSlug/issues/<blocked>/dependencies/blocked_by" -X POST -F "issue_id=$blockerId"
```

Verify each write with `gh api "repos/$repoSlug/issues/<parent>/sub_issues"` or `gh api "repos/$repoSlug/issues/<blocked>/dependencies/blocked_by"`.
